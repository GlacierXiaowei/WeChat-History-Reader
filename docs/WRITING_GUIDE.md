# 文档与文案分工说明

本文档记录本项目不同 Markdown 文件的受众、职责和修改边界，避免把用户文案、开发者资料和 AI 指令混在一起。

## 文件职责

| 文件或目录 | 面向对象 | 主要职责 |
|---|---|---|
| `README.md` | GitHub 用户 | 介绍产品、安装方式、首次使用和面向开发者的公开技术资料。 |
| `README.en.md` | 英文用户与开发者 | 与中文 README 保持内容对应，按英文读者习惯翻译，不擅自改变产品定位。 |
| `dist/RELEASE_NOTES_*.md` | 版本升级用户 | 说明本次版本带来的功能、体验和安装变化，使用面向用户的发行文案。 |
| `docs/releases/` | 项目维护者 | 保存版本说明的长期记录；如需对外发布，应明确采用哪一份发行说明。 |
| `skills/**/SKILL.md` | AI Agent | 描述 AI 如何识别需求、调用本地脚本、解释参数、处理错误和遵守安全边界。 |
| `AGENTS.md` | Codex、GitHub 审查智能体及其他代码 Agent | 提供仓库级的工程、隐私、安全、测试和代码审查约束。 |
| `docs/` 中的其他说明 | 开发者与维护者 | 记录实现细节、兼容性、架构和工作约定，不替代 README 的用户介绍。 |

## `AGENTS.md` 的定位

`AGENTS.md` 不是只给某一个审查智能体看的产品文档。它是仓库级 Agent 指令：

- Codex 会把仓库中的 `AGENTS.md` 作为工作指令读取。
- GitHub Copilot code review 也支持读取仓库根目录的 `AGENTS.md`，用于共享代码审查和工程约束。
- 其他 GitHub 或第三方 Agent 是否读取，取决于其具体集成方式，不能只凭文件名保证。

因此，`AGENTS.md` 适合写“如何审查和修改代码”，不适合写宣传文案、发行公告或面向用户的解释。当前文件中的隐私、安全、运行时和审查规则应继续保留，不应被 README 的营销表达覆盖。

## 三类内容的边界

### 面向用户

用户区要让读者快速理解产品能做什么、如何安装、第一次如何使用，以及它能解决什么问题。可以有适量 emoji、自然的宣传语和具体使用例子，但不要出现内部实现指令或“让 AI 必须如何执行”的提示词。

### 面向开发者

开发者区要说明依赖、环境、目录结构、CLI 工具、参数、JSON 返回约定和贡献方式。内容应准确、简洁、可查证；可以引用源码和脚本，但不应把开发者 API 表格写成面向普通用户的宣传文案。

### 面向 AI Agent

AI 区要说明触发条件、调用顺序、参数选择、诊断边界、错误处理、敏感数据规则和本地脚本路径。它服务于 Agent 的正确执行，不追求营销语气，也不应直接复制到 README 的用户区。

## 修改和冲突处理

1. 用户对当前文件的直接修改意见优先；没有明确授权时，不重写用户已经写好的正文。
2. 修改代码或仓库行为时，遵守 `AGENTS.md` 的工程、隐私和安全约束。
3. 修改 README 或发行说明时，使用本文档的受众划分和文风边界，但保留原作者的表达风格。
4. 本文档是参考记录，不会因为存在于 `docs/` 就自动成为所有 Agent 的强制指令；若希望 Agent 每次编辑文档都读取它，需要由任务提示或明确的 Agent 规则引用它。
5. README、发行说明和 `SKILL.md` 的内容不能互相替代：用户文案不能承担 AI 指令，AI 指令也不能直接当作用户文案。

## 当前约定

- README 的用户部分以中文作者版本为准，除非明确要求，不做整体改写。
- README 的开发者部分可以持续补充，但应保持技术事实与当前代码一致。
- 英文 README 在中文版本确认后再同步。
- 发行说明只记录已经实现、验证或明确属于本版本的变化，不使用未经测量的性能承诺。
- `docs/releases/`、`dist/RELEASE_NOTES_*.md` 和其他发行文案可以作为本地参考资料保留，用于下一次发布时沿用格式；除非明确要求，不自动放入插件 ZIP 或发布附件。
